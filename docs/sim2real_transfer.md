# 恐龙四足机器人 - Sim2Real Transfer 指南

## 什么是 Sim2Real Transfer

Sim2Real Transfer（仿真到真实迁移）是指将 PyBullet 仿真中训练/调好的控制策略，
部署到真实物理机器人上并保持正常工作的过程。

核心挑战：**Reality Gap（现实差距）**——仿真中完美行走的策略直接部署到实机往往失败。

---

## Reality Gap 的来源

| 仿真假设 | 真实情况 | 影响 |
|----------|---------|------|
| 舵机瞬间到达目标角度 | DS3218 响应延迟 ~0.15s/60° | 动作滞后，步态失调 |
| 关节无间隙 | 3D 打印件装配间隙、齿轮回差 | 位置精度下降 |
| 地面完美平坦 | 地面不平、摩擦系数不均 | 滑动、绊倒 |
| 传感器无噪声 | MPU6050 有漂移和噪声 | 状态估计不准 |
| 质量/惯量精确 | 实际重量分布与 URDF 有偏差 | 重心偏移、动力学不匹配 |
| 控制频率稳定 50Hz | 树莓派 I2C 通信有抖动 | 控制周期不均匀 |
| 碰撞为刚体 | 脚垫有弹性、关节有柔性 | 接触力学不同 |

## 三层解决方案

### 第一层：Domain Randomization（仿真端）

在 PyBullet 训练时故意加入随机扰动，让策略"见过各种糟糕情况"，
到实机上就不容易崩。

#### 需要随机化的参数

```python
# 在 rl/dino_env.py 的 reset() 中加入随机化
randomization_ranges = {
    # 动力学参数
    "body_mass":       (1.2, 1.8),    # kg, 标称 1.5 ±20%
    "friction":        (0.4, 1.0),    # 地面摩擦系数
    "joint_damping":   (0.01, 0.1),   # 关节阻尼
    "joint_friction":  (0.0, 0.05),   # 关节摩擦

    # 执行器特性
    "action_delay":    (1, 3),        # 控制步延迟 (模拟舵机响应)
    "action_noise":    (0.0, 0.02),   # 动作噪声 (rad)
    "torque_scale":    (0.8, 1.2),    # 扭矩缩放

    # 传感器噪声
    "imu_accel_noise": (0.0, 0.5),    # m/s² 加速度噪声
    "imu_gyro_noise":  (0.0, 0.05),   # rad/s 角速度噪声
    "imu_gyro_drift":  (0.0, 0.01),   # rad/s 陀螺仪漂移

    # 环境
    "ground_slope":    (-5, 5),       # 度, 地面倾斜
    "push_force":      (0, 3),        # N, 随机侧向推力
}
```

#### 随机化策略

- **均匀随机化**：每次 reset() 时从范围内均匀采样
- **渐进式**：训练前期不加或少加随机化，后期逐渐增大范围
- **相关性**：某些参数可以关联随机化（如质量增大时惯量也增大）

### 第二层：System Identification（实机端）

用实际硬件数据修正仿真模型，缩小仿真与现实的差距。

#### 2.1 质量/惯量标定

```

1. 电子秤称量每个零件实际重量
2. 更新 urdf/dino.urdf 中的 mass 和 inertia
3. 安装完成后称量整机重量
4. 用吊线法测量实际重心位置

需要记录：
  部件              设计值(g)   实测值(g)
  ────────────────────────────────────
  机身框架          120         ?
  树莓派 3B          45         ?
  PCA9685           15         ?
  电池              280         ?
  单个 DS3218        60         ?
  ...
  总重              1500         ?
```

#### 2.2 舵机响应曲线

```python
# 在实机上测量舵机实际响应特性
# 发送阶跃信号，记录到达时间

# - 回差测量：正转到 90° 再反转回来，偏差多少度

# - maxVelocity

```

#### 2.3 IMU 噪声特性

```bash

python3 hardware/04_imu_test.py > imu_static_60s.csv

# 分析：
# - 加速度计零偏 (bias)

```

#### 2.4 地面摩擦测量

```
简易方法：
1. 将机器人脚垫放在目标地面上

```

### 第三层：渐进式部署（实机端）

不直接跑完整策略，分步验证，逐步提高复杂度。

```
Step 1: 站立
  └─ 验证 IK 角度映射正确
  └─ 脚本: hardware/05_stand_test.py
  └─ 通过标准: 四脚着地、机身水平、高度 ~150mm

Step 2: 单腿抬放
  └─ 固定三条腿站立，一条腿做抬起/放下动作
  └─ 验证单腿轨迹跟踪精度
  └─ 确认舵机响应速度够用

Step 3: 慢速 Trot
  └─ 脚本: hardware/06_trot_test.py --slow
  └─ 步幅减半、周期加倍
  └─ 确认基础步态可行

Step 4: 正常速度 Trot（固定步态）
  └─ 脚本: hardware/06_trot_test.py
  └─ 确认动态稳定性

Step 5: 部署 RL 策略（v7 PPO 模型）
  └─ 用 RL 模型输出替代固定步态生成器
  └─ 树莓派上用 ONNX Runtime 推理
  └─ 50Hz 控制循环: IMU 读取 → 模型推理 → 舵机输出
```

## 控制频率适配

### 仿真 vs 实机的频率差距

RL v7 策略的仿真控制频率：
```
PyBullet 物理步进: 240Hz  (dt = 1/240 = 4.17ms)
action_repeat:     2
RL 控制频率:       240 / 2 = 120Hz
RL 控制周期:       8.33ms
```

实机硬件能支持的控制频率取决于信号链路中最慢的环节：

### Phase 1 硬件 (PCA9685 + DS3218) 的频率瓶颈

```
120Hz 控制周期 = 8.33ms，信号链路耗时:

  环节              硬件              耗时        能否满足
  ──────────────────────────────────────────────────────
  IMU 读取          MPU6050 I2C       ~1.5ms      ✅
  RL 推理           Pi 3B CPU (ONNX)  ~5-8ms      ⚠️ 勉强
  舵机指令下发       PCA9685 I2C       ~12ms       ❌ 超时!
  ──────────────────────────────────────────────────────
  合计                                ~19-22ms
  最大可达频率                         ~50Hz

PCA9685 更新 12 个通道的耗时计算:
  单通道: 写 4 字节寄存器, I2C 开销 + Python 驱动 ≈ ~1.0ms
  12 通道 (串行): 12 × 1.0ms = ~12ms
  加上 IMU 共享 I2C 总线: 12ms + 1.5ms = 13.5ms ❌

结论: PCA9685 是 120Hz 的硬性瓶颈，软件优化无法解决。
```

### Phase 2 硬件 (STS3215 + Pi 4B) 的频率能力

```
120Hz 控制周期 = 8.33ms，信号链路耗时:

  环节              硬件              耗时        能否满足
  ──────────────────────────────────────────────────────
  IMU 读取          MPU6050 I2C       ~0.5ms      ✅ (总线空闲)
  RL 推理           Pi 4B CPU (ONNX)  ~2-3ms      ✅
  舵机指令下发       STS3215 SyncWrite ~1.5ms      ✅
  反馈读取 (可选)   STS3215 SyncRead  ~2.0ms      ✅
  ──────────────────────────────────────────────────────
  合计                                ~4-7ms      ✅ 余量充足
  最大可达频率                         ~200Hz+

STS3215 SyncWrite 耗时计算:
  包头(2B) + 广播ID(1B) + 长度(1B) + 指令(1B) + 起始地址(1B)
  + 12 × [ID(1B) + posL(1B) + posH(1B)] = ~42 字节
  42 字节 × 10bit ÷ 1Mbps ≈ 0.42ms
  加上协议开销 ≈ ~1.0-1.5ms ✅
```

### 降频适配方案 (不升级硬件时)

如果暂不升级硬件，可以在实机上降低控制频率：

```python
# 方案 A: 降到 50Hz（PCA9685 安全范围）
# 需要重新训练 RL 策略
# dino_env.py 中修改:
self.action_repeat = 5   # 240/5 = 48Hz ≈ 50Hz

# 影响:
# - 控制延迟从 8.33ms → 20.8ms
# - 步态平滑度下降
# - 可能需要调整 reward 函数中的平滑项权重
# - 对 sim2real gap 的容忍度降低

# 方案 B: 降到 60Hz（PCA9685 极限）
self.action_repeat = 4   # 240/4 = 60Hz

# 需要优化 PCA9685 写入:
# - 使用批量写入模式 (连续寄存器地址)
# - 预计从 ~12ms 压缩到 ~8ms
# - 加上 IMU ~1.5ms 仍然紧张
# - 不推荐，频率不稳定

# 方案 C: 混合方案（推荐的过渡策略）
# Phase 1 用 50Hz (action_repeat=5) 做基础验证
# 确认算法可行后，升级到 Phase 2 硬件跑 120Hz
```

### 不同频率下的性能预估

| 控制频率 | action_repeat | 硬件要求 | 步态质量 | sim2real 难度 |
|---------|--------------|---------|---------|-------------|
| 120Hz | 2 | STS3215 + Pi 4B | 最佳 (仿真同款) | 最低 |
| 60Hz | 4 | PCA9685 极限 | 良好 | 中等 |
| 50Hz | 5 | PCA9685 安全 | 可用 | 较高 (需重训练) |
| 30Hz | 8 | PCA9685 轻松 | 勉强 | 高 (明显延迟) |

### 实机推理

```python
# ===== Phase 1: 50Hz (Pi 3B + PCA9685) =====
import onnxruntime as ort

session = ort.InferenceSession("v7_50hz_policy.onnx")

while running:
    obs = get_observation()  # IMU only (无位置反馈)
    action = session.run(None, {"observation": obs})[0]
    action = np.clip(action, -action_limit, action_limit)
    send_to_servos_pwm(action)      # PCA9685 I2C
    time.sleep(0.02)                 # 50Hz


# ===== Phase 2: 120Hz (Pi 4B + STS3215) =====
import onnxruntime as ort
from SCServo import SMS_STS

session = ort.InferenceSession("v7_policy.onnx")
sts = SMS_STS()
sts.open_port("/dev/ttyUSB0", 1000000)

while running:
    t0 = time.time()

    # 读传感器 (I2C 和 UART 并行无冲突)
    imu_data = read_imu()                          # ~0.5ms
    joint_pos = sts.SyncReadPos([1..12])           # ~2.0ms

    # 推理
    obs = build_observation(imu_data, joint_pos)   # ~0.1ms
    action = session.run(None, {"observation": obs})[0]  # ~2.5ms
    action = np.clip(action, -action_limit, action_limit)

    # 执行 + 安全监控
    positions = action_to_positions(action)
    sts.SyncWritePosEx(ids, positions, speeds, accs)  # ~1.5ms

    # 安全检查 (每 10 帧读一次温度，避免占用带宽)
    if frame_count % 10 == 0:
        temps = [sts.ReadTemperature(i) for i in range(1,13)]
        if max(temps) > 60:
            print("过热保护!")
            break

    # 精确定时
    elapsed = time.time() - t0                     # 合计 ~6ms
    time.sleep(max(0, 0.00833 - elapsed))          # 补齐到 8.33ms
```

## 评估指标

部署后需要对比仿真和实机的性能差异：

| 指标 | 仿真值 (v7) | 实机目标 (50Hz) | 实机目标 (120Hz) | 测量方法 |
|------|-------------|----------------|-----------------|---------|
| 站立稳定性 | CoM 偏移 <2mm | <8mm | <5mm | IMU 积分 |
| 行走速度 | ~0.15 m/s | >0.08 m/s | >0.12 m/s | 秒表 + 距离 |
| Roll/Pitch 幅度 | <5° | <15° | <10° | IMU 数据 |
| 续航时间 | N/A | >60 min | >45 min | 实测 |
| 抗扰能力 | 侧推 3N | 侧推 1N | 侧推 2N | 手动推测 |
| 关节跟踪误差 | 0° (理想) | 未知 (无反馈) | <1° | STS3215 反馈 |
| 控制频率稳定性 | 120Hz 恒定 | 45-55Hz 波动 | 115-125Hz 稳定 | 实测 |
